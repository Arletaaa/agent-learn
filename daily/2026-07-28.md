### Function Calling 实战理解

- 亲眼看到 LLM 返回的 `tool_calls` JSON 格式：
  ```json
  {"name": "duckduckgo_search", "args": {"query": "2026年7月 科技新闻"}}
  ```
- 对比项目一的正则解析 `Thought:` + `Action:` + `Action Input:`：
  - 正则版：容错差，格式稍有偏差就崩溃
  - Function Calling：LLM 原生支持的 JSON，永远精确
- Agent 自动中英文混合搜索（先搜中文，再搜英文关键词），这是框架+Function Calling 自动化带来的能力

### LangChain 框架 vs 手写版对比

| 维度 | 项目一（手写 159 行） | 项目三（框架 ~50 行） |
|------|------|------|
| 工具调用 | `_parse_output()` 正则抠文本 | LLM 返回 JSON `tool_calls` |
| Agent Loop | 自己写 `for step in range(10)` | 框架内置，一行 `invoke()` |
| 搜索工具 | 内置 6 条假数据 | 真实 Web 搜索 API |
| 错误处理 | 无 | 框架自动处理 |
| 消息管理 | 手动 `messages.append()` | 框架自动追加 |

**框架帮你省掉的 100 行 = 解析 + 循环 + 消息管理**

## 心得体会

- Function Calling 是质的飞跃——从"猜 LLM 会输出什么格式"变成"LLM 保证输出标准 JSON"
- 框架的价值不仅在于减少代码量，更在于稳定性——同样的 Agent，框架版永远不会因为 LLM 格式偏差而崩溃
- DuckDuckGo 免费能用但在国内结果有限，对于密集搜索场景还是建议 Tavily 或 SerpAPI
- DeepSeek 的 thinking 模型倾向于过度搜索（8 轮），需要更强的 prompt 约束或更低的 recursion_limit

### Agent Memory 架构设计

- 理解了三种记忆类型：短期记忆（messages 列表）、长期记忆（跨会话持久化）、工作记忆（工具返回结果等临时上下文）
- 核心矛盾：Token 爆炸 → messages 无限增长 → 三种裁剪策略
- 窗口滑动（1 行代码最简单）、自动摘要（LLM 压缩旧消息）、向量检索（语义匹配相关历史）
- 生产级 Memory = 三种混用：窗口（短期）+ 向量（长期）+ 摘要（兜底）
- 通过代码示例理解了如何在项目一上增加 Memory 层

### Message Role 体系

- 理解了四种 role 的定义和作用层级：
  - `system` — 最高指令，定义 Agent 人设、规则、工具
  - `user` — 用户输入 + 传统 ReAct 模式的 Observation
  - `assistant` — LLM 的推理和工具调用决策
  - `tool` — Function Calling 模式的标准化工具结果
- 理解了为什么不能混用：LLM 对不同 role 有固化的训练逻辑
- 对比了项目一（user+Observation）和项目三（tool role）的写法差异
- 掌握了 Role 与 ReAct Loop 的完整映射：system=规则 → user=输入 → assistant=Think → tool=Observe → assistant=答案

### RAG 初步了解

- RAG = Retrieval（检索）+ Augmented（增强）+ Generation（生成）
- 本质：Memory 向量检索思路扩展到外部知识库
- 核心区别：Memory 搜过去的对话，RAG 搜公司文档/论文/网页
- 了解到商业模型（GPT/豆包）不靠纯向量检索，而是大窗口硬扛 + 结构化记忆
