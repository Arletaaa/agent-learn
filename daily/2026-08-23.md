## 引导问题问答记录

### Q1: 多 Agent 存在的根本原因？单 Agent 做不到/做不好的维度？

**用户回答**：单 agent 观点单一，没有协作能力，上下文有限，多 agent 解决这些痛点。

**点评**：
- ✅ "上下文有限" —— 正确，是单 Agent 五大边界之一
- ✅ "观点单一" —— 对应"缺乏第二意见"，方向正确
- ❌ "没有协作能力" —— 属于**循环论证**：只是在复述"多 Agent 有协作、单 Agent 没有"，没有解释为什么需要协作。根本原因是复杂任务超出了单 Agent 在**上下文 / 角色 / 工具 / 串行 / 自纠**五个具体维度上的能力上限，"拆解 + 专业化"能系统性缓解。**协作是手段，不是原因**
- ➕ 遗漏的维度：角色单一（一个 System Prompt 装不下多角色）、工具集耦合（工具越多越易选错）、串行瓶颈（无法并行）
- 一句话本质：多 Agent = 分而治之 + 专业化

### Q2: 四种模式各自解决什么 + 最大代价？

**用户回答**：顺序→上下文有限，代价多次调用；并行→效率慢，代价 token 大；辩论→复杂论述，代价 token 翻倍；层级→有明确层级，代价主管上下文有限。

**点评**：
- ❌ **顺序解决"上下文有限"不准**：顺序模式解决的是**有先后依赖的流水线任务**（调研→分析→写作）。"每步只看自己步骤的上下文"只是顺带收益。代价也不是"多次调用"（所有多 Agent 都多次调用），真正代价是：**总延迟 = 各步之和、无反馈回路（上游错下游跟着错）、单点故障中断全链**
- ⚠️ **并行解决"效率慢"对了一半**：并行解决的是**可拆分的独立子任务 + 多视角覆盖**，提效只是结果之一。代价"token 大"方向对，但最独特的代价是**结果合并难（冲突怎么裁决）+ 汇总者本身成为新瓶颈**
- ⚠️ **辩论解决"复杂论述"表述模糊**：辩论解决的是**事实性 / 推理 / 决策类任务的自我纠错**（多视角互审）。代价"token 翻倍"方向对（成倍增加），还需补充**可能陷入重复争论不收敛、必须设定终止条件**
- ❌ **层级解决"有明确层级"是循环论证**：层级模式解决的是**复杂、目标不明确、需要动态规划**的任务——正因为路由是动态的（主管运行时决定派给谁），才需要 Supervisor；若层级是静态明确的，用顺序/并行就够了。代价"主管上下文有限"是真实问题（主管要汇总所有结果），但**最大的代价是主管单点：判断错则全系统错**

### Q3: project-06 属于哪种模式？LangGraph 怎么表达？

**用户回答**：顺序；不太理解 langgraph。

**点评**：
- ✅ 顺序 —— 正确（研究员→分析师→写作者 = 流水线链）
- 📖 **LangGraph 补课**：StateGraph = **节点 + 边 + 共享状态**。project-06 的画法：3 个节点（researcher / analyst / writer），边 researcher→analyst→writer，加 START/END。CrewAI 用 Task 依赖**隐式**表达顺序，LangGraph 用边**显式**表达——因此更灵活：加一个主管节点 + 条件边，顺序模式就升级成层级模式
- 建议：重读 `09-langgraph.md` 状态图部分，或做一个 5 分钟的节点/边对比图

### Q4: Supervisor 单点瓶颈指什么？缓解手段？

**用户回答**：上下文有限。

**点评**：
- ⚠️ 只答对一小部分。单点瓶颈的核心是**决策单点**：所有子任务的分派、回收、裁决都经过主管，主管判断错 → 全系统错。上下文膨胀只是伴生问题
- ➕ 缓解手段：① 主管只做路由决策不直接干活（内容交 Worker，主管只看摘要）② 结果压缩后再回报（防上下文膨胀）③ 分级主管（层级树，避免单主管管太多）④ 对主管输出加校验 / Guardrail ⑤ 超时 + 重试

### Q5: 单 Agent + 好工具何时更优？判断标准？

**用户回答**：简单任务。

**点评**：
- ✅ 方向正确，但标准要具体化。单 Agent 更优的场景：任务单步可完成 / 对延迟成本敏感 / 工具调用即可覆盖 / 需要确定性高
- 判断标准一句话：**拆的收益（专业化 + 并行）是否大于拆的成本（额外 token + 延迟 + 复杂度 + 错误传播）**。Anthropic 官方建议：先单 Agent + 检索/工具，复杂了再上多 Agent——"用最简单的方案解决"

## 答疑记录

### 问：Supervisor 是什么？

**解答**：Supervisor（主管/编排者 Agent）= 一个"自己不干活、只负责指挥"的 Agent，类比项目经理。

- 流程：接收任务 → 拆解 → 分派 Worker → 回收结果 → 判断（不够再派一轮 / 够了汇总）→ 输出最终答案
- 例子：主管 Agent 接"写多模态调研报告"，拆出 检索/分析/写作，分别派给 research/analysis/writer Worker，发现资料太旧则动态决定再检索一轮，最后汇总
- 与顺序模式区别：顺序是**静态写死的链**（A→B→C 固定）；Supervisor 是**动态路由**，派给谁、是否再派，运行时才决定
- 框架对应：LangGraph = Supervisor 节点 + 条件边形成循环；OpenAI SDK = Handoff 控制权转移；CrewAI = Hierarchical Process 的 manager；Anthropic = Orchestrator-Worker
- 呼应 Q4：主管只决策不干活 → 既是"大脑"也是单点，判断错则全系统错；缓解 = 只看摘要、分级主管、Guardrail、超时重试

### 问：LangGraph 的节点和边怎么判断？

**解答**：判断口诀——**节点 = 动作，边 = 依赖，条件边 = 决策**。

- **节点（做什么）**：一个"原子处理步骤"，有明确的输入→处理→输出。常见类型：一次 LLM 调用、一次工具调用、一段确定性逻辑（判断/汇总/校验）。判断标准：**它是否需要被单独观测、单独复用、单独调试**。两个动作永远一起出现、不需要中间状态 → 合并成一个节点（不是每个函数都是节点）
- **边（谁先谁后）**：B 需要 A 的输出才能开始（数据依赖），或 A 完成后必须执行 B（顺序约束）→ 连边。多上游汇合 = fan-in；一节点发多边 = fan-out（并行分支）
- **条件边（动态决策）**：根据节点输出内容选下一跳。例：Supervisor 判断"结果够不够"→ 够→END，不够→再派 Worker。循环 = 条件边指回上游节点
- 设计流程：① 按处理步骤拆任务 ② 标出需 LLM/工具的步骤 = 节点 ③ 标出依赖 = 边 ④ 找出运行时决策点 = 条件边 ⑤ 需循环/重试 → 条件边指回 ⑥ 多步共享数据 → 用 state 而非强行连边
- 例（project-06）：3 节点 researcher/analyst/writer + 边 researcher→analyst→writer；若加"调研质量校验"，在 analyst 前加校验节点 + 条件边（不合格指回 researcher）

## Skill 引导问题问答记录

### S-Q1: Skill 与普通 Prompt 的本质区别？为什么"不加载就不占上下文"？

**用户回答**：skill 是按需加载，只有触发了才会将内容载入上下文，而 prompt 固定在上下文中。

**点评**：
- ✅ 完全正确。补充两点：① Prompt 是对话上下文里的文本，每次调用都在（除非动态组装）；Skill 是独立文件包，命中 `description` 才被读取注入 ② Skill 额外优势：可版本管理、可多人共享、不污染主对话

### S-Q2: name 和 description 的作用？写太泛/太窄的后果？

**用户回答**：name 是 skill 的名称，description 是触发条件，写太泛会导致无用触发，写太窄会导致需要时不触发。

**点评**：
- ✅ 正确。补充：① name 是"加载/引用的 key"（小写短横线命名），description 是"语义索引卡片"，要写清**做什么 + 何时用 + 何时不用**（反面例子很重要）② 太泛的实际后果：无关任务也触发 → 浪费 token 且指令可能干扰正常行为；太窄：该用时加载不到 → Skill 形同虚设

### S-Q3: Skill 和 MCP 的分工？互补体现在哪？

**用户回答**：skill 负责怎么做，mcp 负责做什么。

**点评**：
- ✅ 方向正确（做法上再精确一点：MCP 回答的是"**能做什么**"——工具能力接入，不是任务本身）。互补实例：调研 Skill 定义"先搜哪个库、怎么构造查询、引用格式"，MCP/检索工具提供执行能力（呼应 `15-rag-agent.md` 的 Skills-guided retrieval）

### S-Q4: 想做的第一个 Skill？

**用户回答**：想做一个"在做决策时不让 LLM 偏向讨好自己"的 skill。

**点评**：
- 🎯 非常好的选题！这在学界叫 **sycophancy（谄媚/迎合）**——LLM 倾向于赞同用户观点、说用户想听的话，是真实存在且有专门研究的现象
- ✅ 该任务完全符合 Skill 选题标准：高频（每次做决策/征求意见都触发）、流程稳定（固定的批判框架）、可标准化（固定检查清单）
- 落地方向：一个"决策质询 / 反谄媚"Skill，规则应包含——必须给出反方论点、检查用户前提假设、不同意时明确说不、区分事实与观点、标注置信度、禁止"你说得对"式开头、按独立标准评估（详见实践环节）

### S-Q5: 制作 Skill 最难的一步？

**用户回答**：最难的是写——如何让 LLM 准确地按照自己的想法走又不消耗太多上下文。

**点评**：
- ✅ 精准的洞察，这正是 Skill 写作的核心张力：**精确性 vs 上下文开销**
- 解法（两条腿）：
  - **精确性**：步骤编号、明确判断标准（if-else 式规则）、正面+反面示例（few-shot）、输出模板约束格式、checklist
  - **省 token**：信息密度优先（呼应 `14-system-prompt-design`）；**渐进式披露（progressive disclosure）**——SKILL.md 正文只留核心规则，大段示例/细节放辅助文件（references/），需要时再读。这正是 Anthropic 官方设计理念："keep SKILL.md concise"
- 记住：写不是一次完成，是**测试迭代**出来的——真实任务上跑，观察偏离，再改
